Role-Gated Portals

Give each side only the screen it actually needs

A company stating a requirement, a company keeping its capability record current, and ConvergX holding both need different things in front of them. What each role can reach is enforced by the application itself rather than assumed from how they signed in.

Request access

01

Give the company asking a place to state the problem

A problem holder works in the view built for stating a requirement and reading what comes back from it. Nothing about any other company's record is on that screen at all.

  • One working view per role
  • Nothing else on screen

02

Give the company answering a place to stay current

A solution provider works in the view built for keeping a capability record accurate, because a capability that was true last year is exactly what produces a bad introduction this year.

  • Keep a capability record current
  • Built for the answering side

03

Give ConvergX the view that carries both sides

ConvergX works in the view that holds the asking side and the answering side together, because ConvergX is the party that has to hold both in order to broker anything between them.

  • Both sides in one place
  • The party that holds both

04

Enforce the boundary in the application itself

What a role can reach is enforced by the application rather than asserted by whatever signed the user in. Read that as a description of how the system behaves, not as an assurance about it.

  • Enforced by the application
  • No third-party audit on record
